# Governance & Controls

**For the auditor who needs to see the controls before they trust the outputs.**

Every governance artifact in this project was generated by an AI agent and approved by a human. The agents do the authoring. The humans do the reviewing. The artifacts are real, structured, and machine-readable.

## 👁️ The Human Approval Gates

There are 4 mandatory human approval points in the pipeline, controlled by a single global toggle:

```python
# src/config.py
REQUIRE_HUMAN_APPROVAL = True
```

When `True`, the pipeline pauses at each gate and waits for human review. When `False` (dev/demo mode), proposals auto-advance -- but all artifacts are still produced.

| Gate | What is reviewed | Who approves | Why it matters |
|------|-----------------|--------------|----------------|
| 👁️ **Business Terms** | New terms proposed by @data-steward agent | Human (project-specific terms) or Auto (external standards like XBRL taxonomy) | Terms define the semantic meaning of every field. A wrong term propagates through all downstream models and DQ rules. |
| 👁️ **Conceptual Model** | Entity-relationship model proposed by @semantic-modeler | Human | Defines what business entities exist and how they relate. Wrong relationships mean wrong joins. |
| 👁️ **Logical Model** | Attribute-level model with data types, nullability, business term mappings | Human | Defines the schema that physical tables must match. Column-level business term assignments drive CDE tagging and DQ rules. |
| 👁️ **DQ Rules** | Proposed data quality rules with SQL, thresholds, and priority levels | Human | DQ rules are structural enforcement -- Iceberg has no constraints. A bad DQ rule either blocks good data (false positive P0) or passes bad data (missed P1+). |

External standard terms (XBRL taxonomy, SEC EDGAR identifiers) auto-approve because their definitions are authoritative. Only project-specific terms (pipeline concepts, derived metrics) require human review.

Source: [`src/config.py`](../../src/config.py), pipeline definition: [`CLAUDE.md`](../../CLAUDE.md)

## Traceability

Every number in the AI-Ready chat traces back to its SEC filing through a documented chain:

```
AI chat answer: "Apple's FY2024 revenue was $394.3B"
    |
    v  tool call: get_company_metric("AAPL", "Revenue", 2024)
    |
    v  DuckDB query against consumable.company_financials
    |
    v  consumable.company_financials row
       (source_fact_id, accession_number, source_concept)
    |
    v  base.conformed_facts row
       (selected from competing facts via concept_priority_rules.json)
    |
    v  base.financial_facts row
       (enriched with fiscal calendar, supersession, amendment tracking)
    |
    v  raw.xbrl_company_facts row
       (as-landed from SEC EDGAR, never transformed)
    |
    v  SEC EDGAR filing
       (accession_number links to the original XBRL document on sec.gov)
```

The `accession_number` field is present at every layer. It is the join key back to the source filing.

## Runtime Lineage

Static lineage documentation is not lineage. It describes what the pipeline *should* do, not what it *did*.

This project captures runtime lineage events in a `governance.lineage_events` Iceberg table. Every promote function emits:

| Event Field | What It Records |
|-------------|----------------|
| `event_type` | START, COMPLETE, or FAIL |
| `run_id` | Pairs START and COMPLETE events for the same execution |
| `event_time` | When the event occurred (UTC) |
| `snapshot_id` | The Iceberg snapshot created by this write |
| `output_row_count` | How many rows were written |
| `dq_passed` | Whether DQ rules passed after the write |
| `duration_ms` | How long the promote took |
| `error_message` | What went wrong (FAIL events only) |

All 11 promote functions are instrumented. The lineage events are themselves stored in an Iceberg table, so they have their own snapshot history.

The static JSON files in `governance/lineage/` are regenerated from runtime data:

```bash
python -m src.infra.lineage generate-docs
```

Source: [`src/infra/lineage.py`](../../src/infra/lineage.py), 13 lineage event files in [`governance/lineage/`](../../governance/lineage/)

## Data Quality Framework

128 SQL-based DQ rules across 9 dimensions. Executed against real Iceberg tables, not mocks.

### DQ Rule Lifecycle

```
PROPOSED  -->  APPROVED  -->  ACTIVE
              |               |
              |  REQUIRE_HUMAN_APPROVAL=True: human reviews
              |  REQUIRE_HUMAN_APPROVAL=False: auto-advance
              |
              v
         Rule executes against real data
              |
              v
         Results stored in governance/dq-results/ (timestamped JSON)
              |
              v
         Scorecard generated in governance/dq-scorecards/ (markdown)
```

### Results by Zone

| Zone | Specs | Rules | Passed | Failed | P0 Gate |
|------|-------|-------|--------|--------|---------|
| Raw | 1 | 8 | 8 | 0 | PASS |
| Base | 5 | 49 | 48 | 1 (P1) | PASS |
| Consumable | 5 | 71 | 71 | 0 | PASS |
| **Total** | **11** | **128** | **127** | **1 (P1)** | **PASS** |

The single P1 failure (BASE-BT-003) is advisory -- comparative data in newer filings legitimately supersedes older filing values, which can violate a temporal ordering assumption. Documented and expected.

### Priority Levels

| Priority | Meaning | Pipeline Impact |
|----------|---------|-----------------|
| P0 | Critical | **Blocks the pipeline.** No data written to Iceberg. |
| P1 | Warning | Logged, documented. Pipeline continues. |
| P2 | Advisory | Informational only. |
| P3 | Monitoring | Tracked for trends. |

### DQ Dimensions Covered

| Dimension | Rule Count | What It Validates |
|-----------|-----------|-------------------|
| Uniqueness | 11 | No duplicate grains, no duplicate record IDs |
| Completeness | 18 | No null values in required fields |
| Validity | 15 | Values within expected ranges and formats |
| Consistency | 19 | Cross-field and cross-table agreement |
| Freshness | 4 | Data recency within expected bounds |
| Referential Integrity | 12 | Foreign key relationships hold |
| Volume | 8 | Row counts within expected ranges |
| Accuracy | 8 | Pipeline filters did not leak (supersession, unit, null BT) |
| Reasonableness | 10 | Financial ratios within evidence-based bounds |

The Accuracy and Reasonableness dimensions were added after the architect review flagged their absence. The Reasonableness thresholds are evidence-based -- EDA revealed real outliers (Netflix Q1 2010 with a 4,862x Operating Margin) that required wider bounds with documented rationale.

Source: 11 rule definition files in [`governance/dq-rules/`](../../governance/dq-rules/), execution engine: [`src/infra/dq_runner.py`](../../src/infra/dq_runner.py)

## Business Glossary

54 business terms defined in a structured JSON glossary. Every term has:
- A unique ID (`BT-001` through `BT-054`)
- A plain-English definition
- Source tier (XBRL taxonomy, SEC EDGAR, or project-specific)
- `is_cde` flag (31 of 54 are Critical Data Elements)
- `is_pii` flag (0 of 54 -- all data is public SEC filings)
- Approval status and approver

Data models store business term *IDs only* (`BT-XXX`). Definitions live in the glossary. Documentation dereferences IDs into human-readable names. One source of truth.

Source: [`governance/business-glossary.json`](../../governance/business-glossary.json)

## Data Models

28 data model artifacts across three levels:

| Level | Count | What It Defines | Approval Gate |
|-------|-------|----------------|---------------|
| Conceptual | 10 | Entities and relationships (ER diagrams) | Human approval required |
| Logical | 9 | Attributes, data types, nullability, business term mappings | Human approval required |
| Physical | 9 | Iceberg column definitions matching logical model | Generated from approved logical |

Every model level includes `Business Term`, `Is CDE`, and `Is PII` columns. CDE and PII flags are derived from the referenced business term in the glossary.

The @semantic-modeler agent auto-detects whether it is working in **greenfield** mode (tables don't exist yet, models proposed before implementation) or **backfill** mode (tables already exist, models reverse-engineered from code). Both modes produce all three model artifacts.

Source: 28 model files in [`governance/models/`](../../governance/models/)

## Audit Trail

Every agent logs its reasoning, not just its outputs. The audit trail captures:
- Why the entity resolver mapped a CIK to a specific company
- Why the tag normalizer classified a concept as Revenue vs Other Income
- Why a DQ rule threshold was set to a specific value
- Why a model relationship was proposed

38 session logs in `docs/sessions/` document every decision, debate, and mistake in the project's construction. These are not sanitized. Problems encountered, workarounds, and failures are recorded alongside successes.

## What a regulator would ask

**Q: How do you know the data has not been tampered with between zones?**
A: Iceberg provides snapshot isolation and immutable data files. Every write creates a new snapshot. Previous versions are always queryable via `AT VERSION` queries.

**Q: How do you trace a specific number in the AI chat back to its source filing?**
A: Every row at every layer carries an `accession_number` that links to the SEC EDGAR filing. The chain: chat answer -> tool call -> consumable row -> conformed_facts -> financial_facts -> raw XBRL -> SEC filing.

**Q: If AI agents are making decisions, where is the human oversight?**
A: `REQUIRE_HUMAN_APPROVAL = True` in `src/config.py`. 4 explicit approval gates. Agents propose; humans approve. The toggle is global and cannot be bypassed per-agent.

**Q: How do you know the DQ rules are actually running?**
A: Timestamped execution results in `governance/dq-results/`. Scorecards generated from real runs in `governance/dq-scorecards/`. Runtime lineage events record `dq_passed` per promote.
