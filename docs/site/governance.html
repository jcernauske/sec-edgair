Governance & Controls

For the auditor who needs to see the controls before they trust the outputs.

Every governance artifact in this project was generated by an AI agent and approved by a human. The agents do the authoring. The humans do the reviewing. The artifacts are real, structured, and machine-readable.

The Human Approval Gates

There are 4 mandatory human approval points in the pipeline, controlled by a single global toggle:

# src/config.py
REQUIRE_HUMAN_APPROVAL = True

When True, the pipeline pauses at each gate and waits for human review. When False (dev/demo mode), proposals auto-advance — but all artifacts are still produced.

GateWhat is reviewedWho approvesWhy it matters
Business Terms New terms proposed by @data-steward agent Human (project-specific) or Auto (external standards like XBRL taxonomy) Terms define the semantic meaning of every field. A wrong term propagates through all downstream models and DQ rules.
Conceptual Model Entity-relationship model proposed by @semantic-modeler Human Defines what business entities exist and how they relate. Wrong relationships mean wrong joins.
Logical Model Attribute-level model with data types, nullability, business term mappings Human Defines the schema that physical tables must match. Column-level business term assignments drive CDE tagging and DQ rules.
DQ Rules Proposed data quality rules with SQL, thresholds, and priority levels Human DQ rules are structural enforcement — Iceberg has no constraints. A bad DQ rule either blocks good data (false positive P0) or passes bad data (missed P1+).

External standard terms (XBRL taxonomy, SEC EDGAR identifiers) auto-approve because their definitions are authoritative. Only project-specific terms (pipeline concepts, derived metrics) require human review.

Traceability

Every number in the AI-Ready chat traces back to its SEC filing through a documented chain:

AI chat answer: "Apple's FY2024 revenue was $394.3B"
↓
tool call: get_company_metric("AAPL", "Revenue", 2024)
↓
DuckDB query against consumable.company_financials
↓
consumable.company_financials row (source_fact_id, accession_number, source_concept)
↓
base.conformed_facts row (selected via concept_priority_rules.json)
↓
base.financial_facts row (enriched with fiscal calendar, supersession, amendment tracking)
↓
raw.xbrl_company_facts row (as-landed from SEC EDGAR, never transformed)
↓
SEC EDGAR filing (accession_number links to the original XBRL document on sec.gov)

The accession_number field is present at every layer. It is the join key back to the source filing.

Runtime Lineage

Static lineage documentation is not lineage. It describes what the pipeline should do, not what it did.

This project captures runtime lineage events in a governance.lineage_events Iceberg table. Every promote function emits:

Event FieldWhat It Records
event_typeSTART, COMPLETE, or FAIL
run_idPairs START and COMPLETE events for the same execution
event_timeWhen the event occurred (UTC)
snapshot_idThe Iceberg snapshot created by this write
output_row_countHow many rows were written
dq_passedWhether DQ rules passed after the write
duration_msHow long the promote took
error_messageWhat went wrong (FAIL events only)

All 11 promote functions are instrumented. The lineage events are themselves stored in an Iceberg table, so they have their own snapshot history.

The static JSON files in governance/lineage/ are regenerated from runtime data:

python -m src.infra.lineage generate-docs

DimensionRulesWhat It Validates

The Accuracy and Reasonableness dimensions were added after the architect review flagged their absence. The Reasonableness thresholds are evidence-based — EDA revealed real outliers (Netflix Q1 2010 with a 4,862x Operating Margin) that required wider bounds with documented rationale.

Business Glossary

54 business terms defined in a structured JSON glossary. Every term has:

  • A unique ID (BT-001 through BT-054)
  • A plain-English definition
  • Source tier (XBRL taxonomy, SEC EDGAR, or project-specific)
  • is_cde flag (31 of 54 are Critical Data Elements)
  • is_pii flag (0 of 54 — all data is public SEC filings)
  • Approval status and approver

Data models store business term IDs only (BT-XXX). Definitions live in the glossary. Documentation dereferences IDs into human-readable names. One source of truth.

What a regulator would ask

Q: How do you know the data has not been tampered with between zones?

Iceberg provides snapshot isolation and immutable data files. Every write creates a new snapshot. Previous versions are always queryable via AT VERSION queries.

Q: How do you trace a specific number in the AI chat back to its source filing?

Every row at every layer carries an accession_number that links to the SEC EDGAR filing. The chain: chat answer → tool call → consumable row → conformed_facts → financial_facts → raw XBRL → SEC filing.

Q: If AI agents are making decisions, where is the human oversight?

REQUIRE_HUMAN_APPROVAL = True in src/config.py. 4 explicit approval gates. Agents propose; humans approve. The toggle is global and cannot be bypassed per-agent.

Q: How do you know the DQ rules are actually running?

Timestamped execution results in governance/dq-results/. Scorecards generated from real runs in governance/dq-scorecards/. Runtime lineage events record dq_passed per promote.
