## Decisions Made

### 1. Two-track pipeline: Raw vs Base/Consumable
The whole conversation started with "WTF is XBRL?" and evolved into a fundamental architectural question: do we have proper data models? The answer was no — we had a conceptual model (CDE catalog) and physical models (data dictionary) but no logical model connecting them.

Jeff's insight was that this mirrors how real organizations mature their data: raw first (quick and dirty), then conceptual, then logical, then physical. The Raw zone stays fast and loose. Base and Consumable zones get the full modeling treatment.

**Why this matters for the blog:** This is the first time the project's "simulate a real data org" philosophy drove a structural change to the agent pipeline itself, not just to the data.

### 2. Single global REQUIRE_HUMAN_APPROVAL toggle
Each pipeline module (entity_resolution, tag_normalization) had its own `REQUIRE_HUMAN_APPROVAL = True`. Jeff asked if the existing "global setting" could also control the new modeling gates. It wasn't actually global — each module had its own copy. We centralized it into `src/config.py` so one boolean controls ALL human-in-the-loop gates: entity resolution, tag normalization, AND the new model progression.

**Why this matters:** One toggle to switch the entire project between "production mode" (humans approve everything) and "dev/demo mode" (auto-advance). This is exactly how real orgs manage governance toggles.

### 3. @semantic-modeler rewrite, not a new agent
The existing `@semantic-modeler` was focused on dimensional modeling (star/snowflake schemas). Rather than creating a new agent, we rewrote it to handle the 3-stage progression. The dimensional modeling output format lives inside Stage 2 (logical) and Stage 3 (physical). Less agent sprawl, more capability per agent.

### 4. Governance reviewer as the enforcement mechanism
Rather than building approval logic into the `@semantic-modeler`, we made `@governance-reviewer` the enforcement point. It blocks pre-implementation review if models are missing/unapproved (Base/Consumable only). This keeps the pattern consistent: governance-reviewer is always the gatekeeper, semantic-modeler is always the proposer.

## Problems Encountered
- The "global" `REQUIRE_HUMAN_APPROVAL` setting wasn't actually global — it was duplicated in two config files. Easy fix once discovered, but it's the kind of thing that would've bitten us when a third module copied the pattern.
- No problems with the config refactor — 175 tests passed on first run because the tests use `apply_gate()` with explicit parameters rather than importing the constant directly. Good test design paying off.
