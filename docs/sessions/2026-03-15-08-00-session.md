```
I need you to design the right AI architecture for "chatting with" a structured financial dataset. The user wants to ask natural language questions and get accurate answers.

**What we have:**
- 5 consumable Iceberg tables in DuckDB (125K total rows):
  - company_financials: 26,894 rows — one row per (company, business_term, fiscal_year, fiscal_period) with val, sector, ticker, etc.
  - financial_ratios: 6,544 rows — computed ratios (net margin, D/E, etc.)
  - period_over_period: 65,445 rows — YoY change, YoY % change, 5yr CAGR
  - peer_comparison: 26,559 rows — sector ranks, percentiles, averages
  - amendment_analysis: 371 rows — restatement patterns per company/year
- 20 large-cap US companies (AAPL, MSFT, AMZN, etc.)
- 25 financial metrics, 17 years of data (2009-2026)
- All tables have clean schemas, business term IDs, company metadata
- Stack: Python 3.11+, DuckDB, Apache Iceberg

**The user's goal:** "Chat with the data" — ask questions like:
- "What was Apple's revenue in 2024?"
- "Compare Apple and Microsoft's profitability"
- "Which company has the fastest revenue growth?"
- "Is Boeing's financial health deteriorating?"
- "Which sector is most profitable?"

**The insight manager proposed 7 AI-Ready specs:** company profiles (JSON docs), metric context registry, anomaly registry, financial narratives, comparison packs, sector summaries, embeddings. But the user is questioning whether this is the right approach.

**Your task:** Design the RIGHT architecture. Consider:

1. **Text-to-SQL** — LLM generates SQL against the consumable tables directly. The data is structured and clean. Is this this the best primary path?

2. **RAG with embeddings** — Embed documents, retrieve, generate. But the data is structured numbers, not unstructured text. Does RAG even make sense here?

3. **Tool use / function calling** — Give the LLM tools that query the database. More controlled than raw SQL.

4. **Pre-computed documents** — The insight manager's approach. Generate text summaries, then RAG over them. Is this adding unnecessary indirection?

5. **Hybrid** — Some combination.

Be brutally honest about what's actually needed vs. what's over-engineering. This is 125K rows across 5 tables — not a massive unstructured corpus. The schemas fit in a single LLM context window.

Output a clear recommendation with:
- The recommended architecture (and why)
- What's actually needed in the "AI-Ready" zone (if anything)
- What's over-engineering that should be cut
- A concrete implementation plan
- How this would work with Claude as the LLM
```

## Decisions Made

**Tool use over Text-to-SQL:** Raw Text-to-SQL is fragile because the LLM invents column names and misuses joins. A library of validated Python functions that Claude calls as tools gives you the control of typed function signatures with the flexibility of LLM orchestration.

**No RAG, no embeddings:** Retrieval-Augmented Generation is the wrong architecture for structured numerical data with a working query engine. The "retrieval" problem is already solved by DuckDB. Adding a vector store adds infrastructure complexity, stale data risk, and latency with no benefit over a direct query.

**Anomaly flags in system prompt, not a separate Iceberg table:** The known anomalies are finite and static. They fit in 1,000 tokens. Building an Iceberg table, DQ rules, and governance artifacts for a static list of ~20 anomaly flags is governance theater.

**AI-Ready is an application layer, not a transformation zone:** The zone model describes data transformation (Raw → Base → Consumable). AI-Ready does not transform data — it serves it through an interface. Treating it as a zone with Iceberg tables and DQ rules is a category error that produces unnecessary complexity.

**Cut 5 of 7 insight manager specs:** Embeddings, RAG narratives, comparison packs, and sector summary documents are all pre-computations of things the tool layer can produce on demand. The anomaly registry and metric context are better as system prompt content than as queryable Iceberg artifacts.

## Problems Encountered
No implementation problems — this was an architecture review session. The main intellectual tension was between the insight manager's well-reasoned document-oriented approach (which would work) and the simpler tool-use approach (which is more direct). The insight manager's analysis of what the LLM needs is correct; the delivery mechanism it proposed (pre-computed documents + RAG) is the over-engineering.
