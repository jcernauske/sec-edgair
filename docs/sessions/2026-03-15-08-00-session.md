## Decisions Made

**Tool use over Text-to-SQL:** Raw Text-to-SQL is fragile because the LLM invents column names and misuses joins. A library of validated Python functions that Claude calls as tools gives you the control of typed function signatures with the flexibility of LLM orchestration.

**No RAG, no embeddings:** Retrieval-Augmented Generation is the wrong architecture for structured numerical data with a working query engine. The "retrieval" problem is already solved by DuckDB. Adding a vector store adds infrastructure complexity, stale data risk, and latency with no benefit over a direct query.

**Anomaly flags in system prompt, not a separate Iceberg table:** The known anomalies are finite and static. They fit in 1,000 tokens. Building an Iceberg table, DQ rules, and governance artifacts for a static list of ~20 anomaly flags is governance theater.

**AI-Ready is an application layer, not a transformation zone:** The zone model describes data transformation (Raw → Base → Consumable). AI-Ready does not transform data — it serves it through an interface. Treating it as a zone with Iceberg tables and DQ rules is a category error that produces unnecessary complexity.

**Cut 5 of 7 insight manager specs:** Embeddings, RAG narratives, comparison packs, and sector summary documents are all pre-computations of things the tool layer can produce on demand. The anomaly registry and metric context are better as system prompt content than as queryable Iceberg artifacts.

## Problems Encountered

1. **Fiscal year derivation was wrong (critical bug)** — The XBRL `fy` field reflects the filing year, not the reporting year. Apple's FY2025 10-K includes comparative FY2024 and FY2023 data, all tagged `fy=2025`. Verification against known 10-K figures revealed only 5/16 matched. Fix: derive fiscal_year from `end_date` + company's `fiscal_year_end_mmdd`. After fix: 15/16 matched.

2. **TTM trailing-twelve-month data masquerading as FY** — XBRL quarterly filings include TTM values with ~365-day durations tagged as FY. Amazon's FY2023 Net Income showed $4.3B (a TTM ending Mar 2023) instead of $30.4B (the actual calendar-year FY2023). Fix: added `_apply_ttm_dedup()` that prefers the row whose end_date month matches the company's fiscal year end. After fix: 16/16 matched.

3. **DQ rule BASE-BT-003 false positive** — Rule assumed superseded facts always have earlier filed_date than their superseder. Comparative data legitimately violates this (a 2025 filing's comparative FY2023 data supersedes the original 2023 filing). Fix: demoted from P0 to P1.

4. **Fiscal calendar mismatch** — After fixing fiscal_year in financial_facts, the fiscal_calendar builder still used raw XBRL fy/fp. Fix: imported same `_derive_fiscal_year()` and `_derive_fiscal_period()` functions.

5. **Three rebuild cycles** — Each fix required dropping all 8 base+consumable Iceberg tables and rebuilding from scratch. The dedup guards prevented incremental updates since fact_id doesn't include fiscal_year.
