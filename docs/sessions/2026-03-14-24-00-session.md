## Decisions Made

### 1. Iceberg has no constraints — DQ is structural, not optional
**THE critical insight of this session.** First DQ run found 3 duplicate CIKs (JPMorgan, Apple, Microsoft) in `base.entity_mappings`. The promote code did a blind `append_data` without checking for existing rows. In Postgres, a `UNIQUE` constraint would have raised an exception. In Iceberg, it silently succeeded. This means:
- The DQ framework isn't a compliance layer — it's doing the job of database constraints
- Every write path needs a check-before-write guard (preventive) AND a DQ rule (detective)
- This applies to every zone going forward: Consumable and AI-Ready

### 2. Dedup guards on every write path
Every promote/ingest function now checks for existing data before appending:
- Raw ingest: grain-level `(cik, accession_number, concept, unit, end_date)` — NOT CIK-level, because new filings for existing CIKs must flow through
- Entity resolution: CIK-level (correct — one company per CIK, forever)
- Tag normalization: concept-level (correct — one CDE per concept, forever)
- Financial facts: `fact_id` (SHA-256 of grain — new filings get new IDs)
- Fiscal calendar: `calendar_id` (SHA-256 of grain)
- Amendment tracking: grain-level `(cik, concept, unit, end_date, original_accession, amendment_accession)` — NOT `tracking_id` which is a UUID regenerated each run

### 3. Raw ingest dedup is grain-level, not CIK-level
Initial implementation deduped on CIK, which meant "once Apple is ingested, never ingest Apple again." That's wrong for production — Apple files new 10-Qs and 10-Ks. Fixed to dedup on the fact grain so new filings flow through while duplicates are blocked.

### 4. Amendment tracking dedup is grain-level, not tracking_id
`tracking_id` is a UUID generated fresh each pipeline run by `detect_amendments()`. Deduping on it is useless — every run generates new UUIDs. Fixed to dedup on the amendment pair grain.

### 5. load_date column on every table
Three temporal axes, not two:
- **Business time** (`filed_date`, `end_date`) — when it happened in the real world
- **System time** (`load_date`) — when our pipeline learned about it (DATE, not TIMESTAMP)
- **Iceberg time** (snapshots, `ingested_at`, `promoted_at`) — which specific pipeline run

`load_date` is the same column name, same meaning, every table, every zone. DATE type for partitioning. Per-zone (raw load_date ≠ base load_date). Existing timestamps (`ingested_at`, `promoted_at`) kept for microsecond precision.

### 6. DQ triggers fire automatically after promote
`validate_after_write()` runs DQ rules after every promote operation. P0 failures raise `DQValidationError`. The data is already written (Iceberg has no transactions), but the caller gets a loud exception. Financial facts model runs DQ once after all 3 tables are written (not after each).

### 7. Table reference extraction uses known namespaces
Initial regex matched `r.cik` and `m.status` as table references. Fixed to only match known Iceberg namespaces (`raw`, `base`, `consumable`, `ai_ready`).

### 8. shields.io badges in README
Static badges that auto-update via `python -m src.infra.dq_runner badge`. Colors: green (all pass), yellow (≥90%), red (<90% or P0 fail).

## Problems Encountered

### 1. First DQ run found real data corruption (BASE-ER-002)
3 duplicate CIKs in `base.entity_mappings`. Root cause: entity resolution pipeline ran twice — first promoted 3 companies, second promoted all 20, creating duplicates for the overlap. Mapping IDs also collided (ER-001 appeared twice meaning different companies). Fixed by deduplicating the table via overwrite and adding the dedup guard to prevent recurrence.

### 2. Table reference regex matched alias.column
`_extract_table_refs` regex `\b([a-z_]+)\.([a-z_]+)\b` matched `r.cik`, `m.status` as namespace.table refs, causing "Table does not exist: r.cik". Fixed by restricting to known namespaces.

### 3. Catalog path was wrong in config.py
Initially set `CATALOG_PATH = data/catalog.db` but the shared catalog lives at `data/catalog/catalog.db`. Each zone has its own warehouse but they share one catalog.

### 4. Amendment tracking dedup failed silently
`tracking_id` is a UUID generated each run. Dedup guard matched on it, found no matches (new UUIDs ≠ old UUIDs), and appended everything. 264K rows became 528K. Fixed to dedup on the amendment pair grain instead.

### 5. DQ validation crashed tests (missing tables)
`validate_after_write` in promote functions tried to load tables that don't exist in test environments (e.g., `raw.xbrl_company_facts` referenced by cross-table DQ rules). Fixed: table registration is now non-fatal (missing tables → individual rule errors), and `validate_after_write` only raises on real P0 failures, not table-loading errors.

### 6. Test fixtures needed load_date
Adding `load_date` as `required=True` in schemas broke 10 tests that built records without it. Fixed by adding `load_date: datetime.date.today()` to all test fixture helpers.
