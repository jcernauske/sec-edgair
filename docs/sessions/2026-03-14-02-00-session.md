## Decisions Made
1. **37 exact mappings curated from actual data** — queried raw.xbrl_company_facts to find the top concepts by company count and fact count. The exact mappings cover the concepts that appear in 15-20 of our 20 companies. Data-driven, not theoretical.
2. **Reused entity_resolution.staging completely** — no staging.py in this module. The staging interface is domain-agnostic (dicts with status/mapping_id/confidence). This saves ~150 lines of code and means staging bugs only need to be fixed once.
3. **Tier 3 bypasses the gate** — writing 3,000+ unmapped concepts with status="unmapped" directly. Requiring human approval for unmapped concepts would make the gate unusable.
4. **Heuristic categories for unmapped** — even concepts we can't map to a CDE get rough categorization via substring matching (e.g., "Tax" → income_statement/tax). This enables coverage analysis by financial statement for all 3,285 concepts.
5. **Pattern rules are conservative** — only 5 regex patterns, intentionally cautious. Better to leave a concept unmapped than to miscategorize it. Prefix rules (19 entries) are more reliable.

## Problems Encountered
1. **DuckDB SQL quoting** — first raw data query failed because `us-gaap` in a WHERE clause was interpreted as a column reference (double-quoted in Python). Fixed by using single quotes in the SQL string.
2. **No problems in implementation** — the entity_resolution module set a very clean pattern. config/schema/core/promote/cli structure is proven. The main work was curating the mapping rules from actual data, which is domain work, not engineering.
